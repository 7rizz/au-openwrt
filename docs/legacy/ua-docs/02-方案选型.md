# 02 · 方案选型：UA2F 还是 UA2F

## 一句话结论

**优先 UA2F。** 除非你的路由器跑不动，或你只想改 UA、其它用防火墙脚本补齐，才选 UA2F。

---

## 全面对比

| 维度 | UA2F | UA2F |
| --- | --- | --- |
| 定位 | 通用 HTTP(S) 重写代理（改 UA 只是功能之一） | 专门的 UA 修改器（内核态 netfilter） |
| 实现方式 | 用户态，SOCKS5 / HTTP / TPROXY / REDIRECT / NFQUEUE | 内核模块 + netfilter queue |
| 与 Clash 共存 | **天生可以**（Clash 把流量转给 UA2F 即可） | 会抢流，需要额外处理，容易冲突 |
| 安装难度 | 官方 ipk/apk，LuCI 点几下 | 官方 ipk 也有了，但配置更"硬核" |
| 覆盖端口 | 任意端口（解析 TCP 流判定是否 HTTP） | 任意端口 |
| 附加能力 | 固定 TTL、清 TCP 时间戳、IPID 归零、封 QUIC、TCP 初始窗口、Desync 抗 DPI、MitM | 只有改 UA |
| 资源占用 | 略高（用户态解析） | 低（内核态） |
| 适合 | 大多数 OpenWrt 路由器、追求省心 | 低配老路由器、或只缺 UA 这一项 |

---

## 决策树

```
你有 OpenWrt 路由器吗？
├─ 没有 / 不想折腾路由器
│    └─ 用客户端重写规则应急（见 03 文档最后一节），但覆盖不全
└─ 有
     ├─ 想省事，还要顺便把 TTL / 时间戳一起办了
     │    └─ ✅ UA2F（推荐）
     ├─ 路由器很弱（内存 <128MB、老款百兆）
     │    └─ ✅ UA2F + firewall-antidetect.sh 补 TTL
     ├─ 学校有 DPI，需要加密防检测
     │    └─ ✅ Clash 加密代理 + UA2F 兜底
     └─ 只需要改 UA，其它都不管
          └─ ✅ UA2F
```

---

## 为什么 UA2F 能和 Clash 共存（UA2F 不行）

UA2F 靠 netfilter/iptables 把流量重定向进队列，**会跟 Clash 抢同一个流**，所以历史上要搞
"二级路由"才能让两者共存。

UA2F 的思路完全不同：它自己就是一个 SOCKS5 代理，由 Clash 通过规则
`MATCH,ua2f` 把流量**主动转发**给它，处理完再发出去。同一条链路上 Clash 在前、UA2F 在后，
职责清晰，还能顺手让一部分流量走加密代理。这也是作者提出 UA2F 的初衷。

```
终端 ──► Clash ──► UA2F ──► 直连 / 加密代理
         (分流)    (改 UA + L3)
```

## 组合建议（按学校检测强度）

| 学校检测强度 | 推荐组合 |
| --- | --- |
| 只查 TTL | UA2F 固定 TTL，或纯防火墙脚本 |
| 查 TTL + UA（最常见） | **UA2F 单机搞定**（TPROXY/REDIRECT 模式，不依赖 Clash） |
| 再加时钟偏移 / IPID | UA2F 额外开 `tcpts` / `ipid` |
| 有 DPI | Clash 加密代理 + UA2F（`DST-PORT,80` 规则 + `MATCH,ua2f`） |

具体部署见 `docs/03-UA2F部署教程.md`（主）与 `docs/04-UA2F部署教程.md`（备）。
